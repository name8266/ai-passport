# 金币推土机：180实体上限与计算模拟（2026-10-17）

## 调整范围
- **物理实体硬上限 180**，开局目标 **156**，为皇冠及双塔等事件留 **16** 个保留槽位。
- 金币自动补充阈值 120；拥堵循环阈值由 264/224 改为 160/136。
- 延迟筹码、奖品、克隆不再硬编码 82；侧塔不再硬编码 64。
- 接触池 2304 → 2048（单条 `contact_t` 40 字节，约节省 10 KiB）。
- 保留早期 `board_v1` 成绩；新版独立存于 `board_v3_180`，继承已发现遗物。
- 实验性快照解码允许合法 `CP_CHIP` 枚举（并不代表当前固件支持断电续局）。

## 数学上限及可重现计算
运行 `python3 tools/model_pusher_capacity.py`。
- 开局实体：256 → 156，数量比例 0.6094。
- 两两组合数：32640 → 12090，比例 0.3704。
- 10 列 × 3 行的规则错列堆叠**代理模型**：XY 候选 3756 → 1335（0.3554）；三维近邻 1117 → 631（0.5649）。
- 模拟计算的是静态几何配对工作量，**不是**原版碰撞求解器的周期、内存峰值或硬件 FPS。
- Amdahl 模型 `S = 1/(1-f+f*r)`，若原帧时间的 50% 受影响：
  - 按逐实体线性成本假定，约 1.243 倍；
  - 按理想二次成本上限，约 1.459 倍。
  - 用户补充：**原版最拥挤时实测仅约 6 FPS**。沿用上述 50% 受影响假设，数学模型对应约 **7.5–8.8 FPS**，并非达到 20 FPS；若 75% 的帧耗时受影响，约 8.5–11.4 FPS。这仍只是结构性估计，真实收益取决于碰撞接触密度及帧时间构成。
- 真正瓶颈可能转移到显示 SPI、FPU、顶点贴图和音频/NVS，必须依 `DENSE_FRAME` 和 `heap` 串口数据判断。

## 回归测试与验收
`./tools/validate.sh --static` 包含：
1. 原有刚体、SAT、堆叠、特殊硬币、5 幕、渲染一致性与持久化测试；
2. 156 个起始实体及连续 30 秒支持稳定性；
3. 在密集状态下实际请求第五幕皇冠/双塔；
4. 在高于旧阈值 82 的状态下请求克隆、延迟蓝筹码；
5. 保留槽位满额时不扣付费金币；
6. `CP_CHIP` 快照合法性；
7. 新旧排行榜相互隔离及遗物解锁继承；
8. 确定性运算量模型输出断言。

`./tools/validate.sh --firmware` 由 ESP-IDF 5.5.3 验证编译。GitHub Actions 工作流配置为对本特性分支 push 自动检测。

**实机验收仍必须补充**：连续 60 秒 `>=150` 实体帧率（需在本版测量，旧版最拥挤时约6 FPS），P99 帧间隔、最低内部堆与最大连续内存块、皇冠出现、静音/恢复及断电重启。不能以主机测试代替实机验证。

## 2026-10-17 二阶段热点优化：支撑点快速路径
- 对普通八边形实体，`gsupport()` 原来对 8 个候选顶点全部执行三维变换和投影；现采用本地 Q12 二维打分，再仅变换一个获胜顶点。
- 若第一、第二名分数差 `<=16`（量化整数），回退原先的 8 顶点精确比较。
- `tests/test_pusher_support_fastpath.py` 模拟 **50,000** 组确定性伪随机空间方向与刚体姿态。当前本地运行验证：**2035** 次回退（**4.07%**），有 **61** 个直接快速选点与精确法不一致的边界案例，全部经回退得到与精确法相同的选择。
- 因此按测试模型，约 **95.93%** 的支撑点查询仅进行一次三维顶点变换。这只是某个函数内部的运算削减，不能据此推断整机 FPS 或碰撞仿真的总体加速比。
- 真实 C 固件回归、长局数物理稳定性以及 ESP32-C3 实测仍待 CI 与设备验证。

## 2026-10-17 三阶段优化：纵向宽相筛选与逐步计时

- `pairs()` 在完整的 SAT 与 pair-cache 检查之前，先验证两枚刚体高度方向的 AABB 间隔；如果相隔超过本步相对竖直速度可能覆盖的距离，则无需调用 SAT。保留旧的高速穿越薄币检测路径。
- 本地实际运行 `tests/test_pusher_vertical_cull.py`，250,000 组确定性随机 Q8 范围/半厚度/速度，结果 **PASS**：192,802 个不可能相遇的配对被剔除，同时保留 10,352 个可能高速穿越的候选。随机分布的剔除数量不是实际游戏的比例。
- 对规则的156枚错层静态代理模型，1,335 个 XY 候选中约 52.7% 存在明显 Z 间隔（未计更精细速度阈值）；**不代表运行时 SAT 调用或总 CPU 降低52.7%**。
- ESP32-C3 串口增加每10秒 `PERF_MEAN` 统计：`physics_us_per_tick`（每个30 Hz模拟步平均CPU微秒），`draw_us_per_call`，以及 `dense_physics_us_per_tick`/`dense_draw_us_per_call`（150个以上实体）。`STAGE` 增加 `vertical_culls`。
- 修复游戏主循环遗留的 `previous_dense>=250`，与渲染统计阈值统一为 `>=150`；以前180上限版本的这一项始终达不到判定条件。
- **核心验收门槛**：有实际设备串口记录的密集场景帧率 `DENSE_FRAME >=20 Hz`、连续60秒、`overflow=0`、`valid=1`，且30 Hz模拟步平均成本及渲染成本能够稳定在时间预算内。当前无实机串口，尚未满足该门槛。

## ESP32-C3性能验收工具

运行本机已有串口命令 `bench 20261017`（或 `bench 12345`）开始90秒相同种子的自动测试；此模式为练习局，在实体数低于150时使用**真实的受限投币入口**补充普通金币，保留16个事件槽位，避免样本过快降为稀疏币盘。不会使用无碰撞的假金币。录下USB串口完整输出到 UTF-8 文本 `设备实测日志.txt`，执行：

```bash
python3 tools/analyze_pusher_perf.py 设备实测日志.txt --min-fps 20 --min-seconds 60
```

检查字段：`DENSE_FRAME` 是150体及以上区间的实测显示帧率，`PERF_MEAN` 分开统计30 Hz物理步与渲染更新的平均CPU耗时，`STATUS` 验证 `overflow=0` 和 `valid=1`。验收采用连续60秒的密集采样，**每个10秒窗口需达到20 FPS**；`physics_us_per_tick` 不应超过33,333微秒。脚本给出通过/不通过，而不是自行猜测帧率。测试逻辑有好/低FPS/溢出/状态失效/样本不足5种合成日志的单元测试。

> 未取得设备USB日志时，当前代码不能判定达到20 FPS。GitHub主机/固件CI也应另行验证。

## 四阶段：零角速度惯量更新跳过

对于本步线/角冲量已经求解完成、角速度的三个整数分量全部严格为0的动态金币，更新位置，但保留原朝向和惯量张量，不再做新的四元数归一化及旋转矩阵计算。旋转中的实体始终使用原精确路径；新统计字段 `orientation_skips` 可用于实机确认节省的次数。这不合并刚体、不跳过线性碰撞求解，也不利用浮点近零阈值。数值上对25万组随机四元数验证了零角速度下的姿态导数恰为0；完整C固件仍须经过CI及硬件运行验证。
