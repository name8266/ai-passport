# Passport 通知中心 Public RC3 · 滚动摘要与防抖验收

> RC3 的重点是实现客户指定的准确时序与内容输出。沿用 RC2 的 NimBLE 及内存安全方案。固件编译与自动测试不替代 iPhone / Wi-Fi / TLS 真机测试。

## 客户确认的触发规则

| 场景 | 行为 |
| --- | --- |
| 用户已读清空后，只有 1～2 条新通知 | 保存在设备内，不自动调用 AI |
| 当前周期累计首次达到 3 条新通知 | 开始 **15 秒（0.25 分钟）** 等待 |
| 等待期内再收到第一条通知 | 在原计划调用时间上 **再延长 9 秒（0.15 分钟）** |
| 等待期内继续收到通知 | 每增加 1 条，继续延长 **5 秒** |
| 从开始等待起累计最多 120 秒 | 到达硬上限，立刻冻结当时已持久化的通知批次并发起汇总，不再延期 |
| API 调用期间又来通知 | 归下一轮等待与总结；不会把它们混入本轮冻结窗口 |
| 已存在未清空的摘要 | 再来 **1 条** 通知即可开始下一轮 15 秒等待及滚动增量更新 |
| 用户点击“已读清空” | 结束整个周期，把未分析的零散通知一并划过处理游标；后续重新从 3 条起算 |
| API 超时、密钥无效、模型格式错误 | 不确认丢弃源通知，下次重试；低内存时不强行执行 HTTPS |

**自动判定仅统计实际写入 Flash 的 ANCS 预览记录，不把尚未取得正文的 BLE 元数据误计为完整通知。**

## 摘要与待办输出

- 当前综合摘要始终只有一份，内容 **1～2 句话**，短而覆盖自上次已读清空以来仍有效的重要信息。
- 增量 API 请求带上此前的综合摘要与结构化未完成事项，再融合此次冻结窗口中新到的预览；不重复传输全部旧通知正文，以适应 ESP32-C3 内存与 API Token 限制。
- 待办只展示实际提取的 **最多 5 条**，按明确期限及紧急程度优先排序；一般希望显示 **3～5 条重要事项**，不足 3 条时如实显示，不虚构。
- 已持久化的旧待办不会因为下一次模型忽略它们而删除。用户可网页逐项完成，或“已读清空”整份周期。
- 任务已满但新消息仅供参考时仍可更新摘要；若真的存在第六个待办，拒绝本次不完整保存并保留原预览，避免静默覆盖。
- 继续使用 RC2 的双槽摘要持久化、ACK 游标重置、归档分区安全磨损均衡。

## 自动化测试与真机检查

主机/ASan/UBSan：15s、首次9s、后续5s、120s上限、无新增时到期执行、新通知超时不延长、手动已读重置；冻结日志序列号后新增事件不进入旧批次；旧待办保留、1～2句校验、优先排序、无真实任务不凑数。

请自行在设备验证：冷启动、已读后前两条不触发、第三条等15秒；分别在第5秒、第9秒投递新通知，确认倒计时递增；高频推送至2分钟内仍正常发起API；确认云端服务不可用时通知仍留存；验证真机最低RAM、最大连续堆、Wi-Fi/BLE 共存、70小时以上持续测试。

本版依旧保留客户指定的开放热点和免登录管理网页；不将其误表述为已经提供密码保护。
